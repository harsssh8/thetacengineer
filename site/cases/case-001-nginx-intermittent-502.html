CASE-001: Intermittent 502 Errors Behind an Nginx Reverse Proxy

Roughly 0.5% of API requests fail with 502 under light load, never under heavy load. A keep-alive timeout race between Nginx and the upstream.

Linux & Infrastructure·18 Nov 2026·10 min read·Fictional case

    01Problem statement

    Approximately 0.5% of API requests through the Nginx reverse proxy fail with HTTP 502 Bad Gateway. Failures happen mostly outside business hours and almost never at peak load.

    02Environment

    ComponentDetail
    Reverse proxyNginx 1.24 on Ubuntu 22.04 — api.example.internal
    UpstreamTwo Node.js 20 API instances, 10.0.8.21:3000 and 10.0.8.22:3000
    Proxy configupstream block with keepalive 32, proxy_http_version 1.1, proxy_set_header Connection ""
    Recent changeUpstream keep-alive enabled on the proxy one week before the first report

    03Reported symptoms

    • Client applications intermittently receive 502 Bad Gateway.
    • Retrying the same request immediately succeeds.
    • Error rate is higher at night and at weekends.

    04Initial observations

    • Both upstream instances are healthy. CPU, memory and event-loop latency are normal.
    • Node.js application logs contain no record of the failed requests. They did not reach the application.
    • The start of the errors lines up with the keep-alive change.
    • Inverse load correlation: fewer requests, more errors. This points to an idle timer rather than capacity.

    05Investigation steps

    1. Quantify and classify the errors in the access log by method, upstream and time.
    2. Read the Nginx error log for the matching timestamps.
    3. Compare idle timeouts on both sides of the upstream connection.
    4. Capture proxy ↔ upstream traffic and find a failing connection.
    5. Form one hypothesis that explains every symptom, including why GET requests are unaffected.

    06Commands executed

    bash — proxy host
    # 502s by HTTP method (combined log format: $6 = "METHOD)
awk '$9 == 502 {print $6}' /var/log/nginx/access.log | sort | uniq -c

# Matching error log entries
grep -E "prematurely closed|reset by peer" /var/log/nginx/error.log | tail -n 5

# Upstream keep-alive configuration on the proxy
nginx -T 2>/dev/null | grep -nE "upstream|keepalive"

# Node.js idle timeout (default 5000 ms unless set)
node -e "console.log(require('http').createServer().keepAliveTimeout)"

# Capture proxy ↔ upstream traffic
sudo tcpdump -i ens160 -nn -w upstream.pcap 'host 10.0.8.21 and port 3000'

    08Packet / log analysis

    In the capture, filtering on tcp.flags.fin == 1 || tcp.flags.reset == 1 and following the failing stream showed:

    1. A request completes at t=0.042 s and the connection returns to Nginx's idle pool.
    2. At exactly 5.000 s of idle time, Node.js sends a FIN.
    3. Within a millisecond, before Nginx processes the FIN, Nginx writes a new POST on the same socket.
    4. Node.js answers with RST. Nginx logs “upstream prematurely closed connection” and returns 502.
    Why only POST and PATCH?

    When an upstream fails, Nginx retries on the next server only for idempotent methods (proxy_next_upstream; since 1.9.13 non-idempotent requests are not retried by default). GET requests hit the same race but were silently retried. POST and PATCH were not.

    09Root cause

    Nginx kept idle upstream connections for up to 60 seconds, but Node.js closed them after 5 seconds. Whenever Nginx reused a connection at the moment Node.js was closing it, the request was reset. Light traffic made this more likely, because connections sat idle long enough to reach the 5-second timer.

    10Corrective action

    nginx — /etc/nginx/conf.d/api.conf
    upstream api_backend {
    server 10.0.8.21:3000;
    server 10.0.8.22:3000;
    keepalive 32;
    keepalive_timeout 4s;   # must be shorter than the upstream's 5 s idle timeout
}

    The rule: the side that reuses connections must give up on them first. The proxy's idle timeout was set below the upstream's. The same result could be reached by raising Node.js keepAliveTimeout above Nginx's, but changing the proxy needed no application release.

    bash
    nginx -t && systemctl reload nginx

    11Validation

    • 24 hours after the change: 0 502 responses in the access log (baseline ≈ 220 per day).
    • grep -c "prematurely closed" /var/log/nginx/error.log on the rotated log returns 0.
    • A new capture shows Nginx sending the FIN after 4 s of idle time, so the upstream never closes a connection the proxy might reuse.

    12Technical lessons

    • Intermittent errors that get worse at low load usually involve an idle timer.
    • Requests missing from the application log never reached the application. Look at the layer in between.
    • Retry behaviour can hide a fault for some methods. Classify errors by method before drawing conclusions.
    • For any proxy with connection reuse, compare idle timeouts on both sides.
