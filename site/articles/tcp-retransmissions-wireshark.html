Investigating TCP Retransmissions with Wireshark

Small requests work but large transfers stall. A step-by-step retransmission analysis that ends at a Path MTU black hole.

Networking & Protocols·20 Nov 2026·12 min read

On this page

    Demonstration content.The environment, addresses and outputs in this article are fictional and were written to illustrate the documentation format. They do not describe a real customer or production incident.

    01Overview

    Interactive SSH sessions to a data-centre file server work normally from a branch office, but uploading files with scp stalls at 0% and eventually times out. Downloads in the opposite direction complete. This article walks through how TCP retransmission analysis isolates the fault to a Path MTU Discovery (PMTUD) black hole.

    02Technical Background

    Every link has a Maximum Transmission Unit (MTU). Ethernet is normally 1500 bytes. Tunnels add headers — IPsec ESP in tunnel mode commonly adds 50–73 bytes — so the usable MTU inside a tunnel is lower, often configured as 1400.

    Modern TCP stacks set the IPv4 Don't Fragment (DF) bit and rely on PMTUD (RFC 1191): when a router cannot forward a packet because it is too large, it drops it and returns an ICMP Type 3, Code 4 — Fragmentation Needed message carrying the next-hop MTU. The sender lowers its path MTU and resends smaller segments.

    If that ICMP message is filtered anywhere on the way back, the sender never learns the smaller MTU. It keeps retransmitting full-size segments that are silently dropped. This is a PMTUD black hole.

    ValueBytesNotes
    Ethernet MTU1500IP packet size, excludes the 14-byte Ethernet header
    IPv4 + TCP headers4020 + 20, without options
    TCP timestamps option12Common on Linux; reduces payload per segment
    Default MSS14601500 − 40
    Payload with timestamps14481460 − 12; the Len=1448 seen in captures

    03Environment / Topology

    • Client: Linux workstation, 10.10.20.25, MTU 1500
    • Server: Linux file server, 10.50.0.40, MTU 1500
    • Path: internal firewall → branch VPN gateway → IPsec tunnel (MTU 1400) → DC VPN gateway

    04Symptoms

    • SSH login, shell commands and directory listings work.
    • scp uploads of any file larger than a few kilobytes stall at 0% and time out after several minutes.
    • scp downloads from the server to the client complete at normal speed.
    • ping 10.50.0.40 succeeds with 0% loss and stable latency (~21 ms).
    Why the symptom pattern matters

    “Small things work, big things hang” is the signature of a size-dependent problem. Generic packet loss would also affect interactive SSH and ping.

    05Possible Causes

    HypothesisWould explainWould not explain
    Packet loss / congestion on the WANRetransmissions, slow transfersWhy ping and interactive SSH are clean; why only one direction fails
    Duplex mismatchRetransmissions, late collisionsDirection-specific, size-specific failure; interface counters were clean
    Firewall session or inspection issueStalled flowsWhy the same TCP session carries small packets fine
    MTU mismatch / PMTUD black holeSize-specific, direction-specific failure—

    06Troubleshooting Methodology

    1. Define the problem precisely. Uploads stall, downloads work, interactive traffic works. One direction, one size class.
    2. Establish a baseline. Confirm latency and loss with ping and mtr to rule out general path problems.
    3. Test the size hypothesis directly. Send pings with DF set at different sizes to find the largest packet that crosses the path.
    4. Capture during a failing transfer. Look at which segments are retransmitted and whether any ICMP arrives.
    5. Compare directions. Explain why downloads succeed — the explanation must fit every symptom.

    07Commands and Tools

    bash — client
    # 1. Baseline latency and loss
ping -c 20 10.50.0.40
mtr -rwc 100 10.50.0.40

# 2. Path MTU test with Don't Fragment set (payload + 28 bytes ICMP/IP header)
ping -M do -s 1472 -c 3 10.50.0.40    # 1500-byte packet
ping -M do -s 1372 -c 3 10.50.0.40    # 1400-byte packet

# 3. Per-socket TCP state, MSS and retransmission counters during the upload
ss -tin dst 10.50.0.40

# 4. Capture headers only on the client during a failing scp upload
sudo tcpdump -i eth0 -nn -s 128 -w upload.pcap host 10.50.0.40

    Useful Wireshark display filters for this investigation:

    FilterPurpose
    tcp.analysis.retransmissionSegments Wireshark identifies as retransmitted
    tcp.analysis.duplicate_ack || tcp.analysis.lost_segmentEvidence of loss as seen by the receiver
    icmp.type == 3 && icmp.code == 4Fragmentation Needed messages (should be present, are not)
    tcp.len > 1300Isolate full-size segments

    08Packet Capture / Log Analysis

    The DF-bit ping test gives the first hard evidence: 1400-byte packets cross the path; 1500-byte packets disappear without any error.

    Three observations from the capture:

    1. Only segments with Len=1448 (1500-byte IP packets) are retransmitted. Smaller segments in the same connection are acknowledged.
    2. The filter icmp.type == 3 && icmp.code == 4 returns no packets on the client.
    3. A simultaneous capture on the branch VPN gateway's LAN interface shows it is sending ICMP Fragmentation Needed (next-hop MTU 1400) towards 10.10.20.25. The message leaves the gateway but never reaches the client.
    Why downloads work

    For downloads, the DC VPN gateway sends Fragmentation Needed to the server. Nothing filters ICMP on the data-centre side, so the server lowers its path MTU and the transfer succeeds. The fault exists only on the branch side of the path.

    09Root Cause

    The internal firewall between the client VLAN and the branch VPN gateway had an ACL that permitted only ICMP echo-request and echo-reply and dropped every other ICMP type. ICMP Type 3 Code 4 messages generated by the VPN gateway were discarded. The client could not complete Path MTU Discovery and kept retransmitting 1500-byte packets that the tunnel could not carry.

    10Resolution

    Two complementary changes were made:

    1. Permit ICMP Fragmentation Needed (IPv4 Type 3 Code 4, and ICMPv6 Type 2 Packet Too Big for IPv6) through the internal firewall. This repairs PMTUD for all protocols.
    2. Clamp TCP MSS on the tunnel to 1360 (1400 − 40) as defence in depth, so TCP sessions negotiate a segment size that fits the tunnel from the first SYN.
    configuration examples
    ! Cisco IOS — tunnel interface on the branch VPN gateway
interface Tunnel10
 ip mtu 1400
 ip tcp adjust-mss 1360

# Linux gateway equivalent (iptables)
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
    Do not block all ICMP

    Filtering every ICMP type is a common hardening mistake. Fragmentation Needed and Packet Too Big are required for correct operation. RFC 4890 gives guidance on which ICMPv6 messages must be permitted.

    11Validation

    The fix was validated with the same evidence that demonstrated the fault:

    output — fictional
    $ ip route get 10.50.0.40
10.50.0.40 via 10.10.20.1 dev eth0 src 10.10.20.25 uid 1000
    cache expires 597sec mtu 1400

$ ss -tin dst 10.50.0.40 | grep -o 'mss:[0-9]*\|retrans:[0-9/]*'
mss:1348
retrans:0/0
    • The client now receives ICMP Type 3 Code 4 and caches a path MTU of 1400.
    • New sessions negotiate a clamped MSS, so the effective payload is 1348 bytes with timestamps.
    • A 2 GB scp upload completes with zero retransmissions in the capture.

    12Key Takeaways

    • Size-dependent, direction-dependent failures point to MTU before anything else.
    • ping -M do -s <size> is the fastest way to measure path MTU from Linux.
    • In a capture, look at which segments are retransmitted, not just how many.
    • Capture at more than one point. The gateway capture proved the ICMP was sent; the client capture proved it was lost.
    • Fix the cause (ICMP filtering) and add resilience (MSS clamping).
