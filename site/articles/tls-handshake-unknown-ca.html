TLS Handshake Failures: Reading the Alert

Browsers connect, API clients fail. Using openssl s_client and Wireshark to find an incomplete certificate chain.

Networking & Protocols·8 Nov 2026·8 min read

On this page

    Demonstration content.The environment, addresses and outputs in this article are fictional and were written to illustrate the documentation format. They do not describe a real customer or production incident.

    01Overview

    A newly renewed certificate on an internal API works in every browser, but Python, Java and curl clients fail with certificate verification errors. The server is sending only the leaf certificate and omitting the intermediate CA.

    02Technical Background

    A client trusts a server certificate by building a chain from the leaf up to a root CA in its own trust store. Root certificates are installed on the client. Intermediate certificates are not — the server is expected to send them in the TLS Certificate message, in order: leaf first, then each intermediate (RFC 8446 §4.4.2).

    Many browsers hide an incomplete chain. They cache intermediates from earlier visits or download them using the certificate's Authority Information Access (AIA) URL. Most programmatic clients do neither, so they fail.

    03Environment / Topology

    ComponentValue
    Serverapi.example.internal — Nginx, TLS 1.2 and 1.3
    ChainLeaf → Example Issuing CA G2 (intermediate) → Example Root CA
    ClientsBrowsers (work); Python requests, Java 17, curl (fail)

    04Symptoms

    client errors — fictional
    # Python requests
requests.exceptions.SSLError: ... [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate

# Java
javax.net.ssl.SSLHandshakeException: PKIX path building failed: ... unable to find valid certification path to requested target

# curl
curl: (60) SSL certificate problem: unable to get local issuer certificate

    The failures started immediately after the certificate was renewed. Browsers show a valid padlock.

    05Possible Causes

    HypothesisCheck
    Client trust store missing the root CADoes the same client trust other certificates from this CA?
    Server sending an incomplete chainopenssl s_client -showcerts: how many certificates are sent?
    Hostname mismatch (SAN)Would produce a different error: hostname mismatch, not an issuer error
    Expired or not-yet-valid certificateWould produce a validity error; check notBefore and notAfter

    06Troubleshooting Methodology

    1. Read the exact error. “Unable to get local issuer” means chain building failed, not a hostname or expiry problem.
    2. Inspect what the server actually sends, using a client that does not fetch intermediates on its own.
    3. Confirm in a packet capture which certificates are in the Certificate message and which alert the client sends.
    4. Verify the chain offline with the CA files before changing the server.

    07Commands and Tools

    bash
    # What does the server send? (-servername sets SNI)
openssl s_client -connect api.example.internal:443 \
  -servername api.example.internal -showcerts </dev/null

# Force TLS 1.2 so the Certificate message is visible in Wireshark
openssl s_client -connect api.example.internal:443 \
  -servername api.example.internal -tls1_2 </dev/null

# Inspect the leaf
openssl x509 -in leaf.crt -noout -subject -issuer -dates -ext subjectAltName

# Verify the chain offline
openssl verify -CAfile root.crt -untrusted intermediate.crt leaf.crt
    Wireshark filterPurpose
    tls.handshake.type == 11Certificate message (visible in TLS 1.2 only)
    tls.alert_messageAny TLS alert
    tls.alert_message.desc == 48Unknown CA alert
    TLS 1.3 and captures

    In TLS 1.3 the Certificate message is encrypted. To see it in Wireshark, force TLS 1.2 on a test client, or decrypt with an SSLKEYLOGFILE from a client you control.

    08Packet Capture / Log Analysis

    openssl s_client — fictional
    CONNECTED(00000003)
depth=0 CN = api.example.internal
verify error:num=20:unable to get local issuer certificate
verify return:1
depth=0 CN = api.example.internal
verify error:num=21:unable to verify the first certificate
verify return:1
---
Certificate chain
 0 s:CN = api.example.internal
   i:C = XX, O = Example Org, CN = Example Issuing CA G2
---
...
Verify return code: 21 (unable to verify the first certificate)

    The chain contains a single certificate (depth 0). Its issuer, Example Issuing CA G2, is not in the client's trust store and was not sent by the server.

    In the TLS 1.2 capture, the server's Certificate message has a certificates length that matches one certificate. The client immediately sends Alert (Level: Fatal, Description: Unknown CA) and closes the connection.

    09Root Cause

    During renewal, the Nginx ssl_certificate directive was pointed at the new leaf certificate file only. The previous configuration used a full-chain file. The server stopped sending the intermediate, so clients that do not cache or fetch intermediates could not build a path to the trusted root.

    10Resolution

    bash — server
    # Build the chain: leaf first, then intermediate(s). Do not include the root.
cat leaf.crt intermediate.crt > /etc/nginx/tls/api.fullchain.pem

# /etc/nginx/conf.d/api.conf
#   ssl_certificate     /etc/nginx/tls/api.fullchain.pem;
#   ssl_certificate_key /etc/nginx/tls/api.key;

nginx -t && systemctl reload nginx
    Order matters

    The leaf certificate must come first. A file with the intermediate first makes Nginx present the wrong certificate, and nginx -t may report a key mismatch.

    11Validation

    output — fictional
    $ openssl s_client -connect api.example.internal:443 -servername api.example.internal </dev/null 2>/dev/null | grep -E "^ [0-9] s:|Verify return"
 0 s:CN = api.example.internal
 1 s:C = XX, O = Example Org, CN = Example Issuing CA G2
Verify return code: 0 (ok)

$ openssl verify -CAfile root.crt -untrusted intermediate.crt leaf.crt
leaf.crt: OK

    Python, Java and curl clients connected successfully. The Wireshark capture shows two certificates in the Certificate message and no alert.

    12Key Takeaways

    • “Works in the browser” does not prove the chain is complete.
    • openssl s_client -showcerts shows exactly what the server sends. Count the certificates.
    • The error text tells you which part of validation failed: chain, hostname or validity.
    • Add a chain check (Verify return code: 0) to the certificate renewal procedure.
