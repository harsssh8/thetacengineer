F5 BIG-IP: Pool Member Marked Down by an HTTP Monitor

The application answers in a browser, yet BIG-IP marks every pool member down. Why the monitor send string and Host header matter.

F5 & Application Delivery·14 Nov 2026·9 min read

On this page

    Demonstration content.The environment, addresses and outputs in this article are fictional and were written to illustrate the documentation format. They do not describe a real customer or production incident.

    01Overview

    After two new Nginx web servers are added to a BIG-IP pool, the HTTP health monitor marks both members down and the virtual server goes offline. Browsing directly to the servers works. The cause is an HTTP/1.0 monitor request with no Host header, sent to servers that use name-based virtual hosting.

    02Technical Background

    A BIG-IP HTTP monitor opens a TCP connection to each pool member, sends the configured send string, and marks the member up only if the response matches the receive string (a regular expression) within the timeout.

    Web servers that host several sites on one IP address select the site from the HTTP Host header. HTTP/1.1 requires a Host header (RFC 9112). An HTTP/1.0 request often has none, so the server falls back to its default virtual host — which may return something very different from the real application.

    03Environment / Topology

    ObjectValue
    Virtual servervs_app_https — 10.1.10.100:443, client SSL profile
    Poolpool_app_http — 10.1.20.11:80, 10.1.20.12:80
    Monitormon_app_http (custom HTTP)
    ServersNginx with server_name app.example.internal; a separate default server returns 404

    04Symptoms

    • tmsh show ltm pool pool_app_http shows both members offline (red).
    • Clients connecting to the virtual server receive a TCP reset.
    • http://app.example.internal/health returns 200 OK in a browser on the server VLAN.
    • The servers' firewall and ports are unchanged; TCP connections from the BIG-IP to port 80 succeed.

    05Possible Causes

    HypothesisHow to test
    No route or ACL between the self IP and the membersTCP connect from BIG-IP to member:80
    Health endpoint actually failingRequest /health directly with the correct Host header
    Monitor send string not what the server expectsReplay the exact send string from the BIG-IP
    Receive string does not match the responseCompare the raw response with the regex

    06Troubleshooting Methodology

    1. Read the monitor log. /var/log/ltm records each state change and, on current versions, the last error.
    2. Read the monitor configuration. Note the exact send and receive strings.
    3. Reproduce from the BIG-IP. Send the identical request from the same source the monitor uses. A browser test is not equivalent.
    4. Capture the monitor traffic to see the real request and response on the wire.
    5. Change one thing, then confirm the member state and log.

    07Commands and Tools

    bash — BIG-IP advanced shell
    # Pool member state
tmsh show ltm pool pool_app_http members

# Monitor definition
tmsh list ltm monitor http mon_app_http

# Monitor state changes
grep -i "monitor status" /var/log/ltm | tail -n 5

# Replay the monitor's exact request (no Host header, HTTP/1.0)
printf 'GET /health HTTP/1.0\r\n\r\n' | nc 10.1.20.11 80

# Same request with a Host header, HTTP/1.1
printf 'GET /health HTTP/1.1\r\nHost: app.example.internal\r\nConnection: close\r\n\r\n' | nc 10.1.20.11 80

# Capture monitor traffic on all interfaces, with payload
tcpdump -nni 0.0:nnn -s0 -A 'host 10.1.20.11 and port 80'
    Why not curl?

    curl always adds a Host header, even with -0 (HTTP/1.0). To reproduce a monitor exactly, send the raw bytes with printf | nc.

    08Packet Capture / Log Analysis

    tmsh list — fictional
    ltm monitor http mon_app_http {
    defaults-from http
    destination *:*
    interval 5
    timeout 16
    recv "200 OK"
    send "GET /health HTTP/1.0\r\n\r\n"
}
    /var/log/ltm — fictional
    Nov 12 10:42:17 bigip1 notice mcpd[6821]: 01070638:5: Pool /Common/pool_app_http member /Common/10.1.20.11:80 monitor status down. [ /Common/mon_app_http: down; last error: /Common/mon_app_http: Response Code: 404 (Not Found) ]
    replay — fictional
    $ printf 'GET /health HTTP/1.0\r\n\r\n' | nc 10.1.20.11 80
HTTP/1.1 404 Not Found
Server: nginx
Content-Type: text/html
Connection: close

$ printf 'GET /health HTTP/1.1\r\nHost: app.example.internal\r\nConnection: close\r\n\r\n' | nc 10.1.20.11 80
HTTP/1.1 200 OK
Server: nginx
Content-Type: application/json
Connection: close

{"status":"ok"}

    The evidence is conclusive: the same server returns 404 without a Host header and 200 with one. The tcpdump output shows the identical behaviour for the monitor's own probes.

    09Root Cause

    The monitor sent an HTTP/1.0 request with no Host header. Nginx routed it to the default server block, which returns 404 for every path. The receive string 200 OK never matched, so the monitor marked every member down. The application itself was healthy.

    10Resolution

    bash — BIG-IP
    tmsh modify ltm monitor http mon_app_http \
  send "GET /health HTTP/1.1\r\nHost: app.example.internal\r\nConnection: Close\r\n\r\n" \
  recv "^HTTP/1\.[01] 200"

tmsh save sys config
    • The request is now HTTP/1.1 with the correct Host header.
    • Connection: Close stops the member holding the monitor connection open.
    • The receive string is anchored to the status line. A bare 200 would also match a 404 page that contains “200” anywhere in its body.
    Change control

    A monitor change affects every pool that uses it. Check usage first with tmsh list ltm pool one-line | grep mon_app_http, and make the change in an approved window.

    11Validation

    output — fictional
    $ tmsh show ltm pool pool_app_http members | grep -E "Ltm::Pool Member|Availability"
Ltm::Pool Member: 10.1.20.11:80
  Availability : available
Ltm::Pool Member: 10.1.20.12:80
  Availability : available

$ grep -i "monitor status" /var/log/ltm | tail -n 2
... member /Common/10.1.20.11:80 monitor status up. [ /Common/mon_app_http: up ] ...
... member /Common/10.1.20.12:80 monitor status up. [ /Common/mon_app_http: up ] ...

    The virtual server returned to available, and test requests through 10.1.10.100 were distributed across both members.

    12Key Takeaways

    • A browser test is not a monitor test. Reproduce the monitor's exact bytes from the BIG-IP.
    • Use HTTP/1.1 with a Host header for monitors in front of name-based virtual hosts.
    • Anchor receive strings to the status line.
    • /var/log/ltm usually contains the answer. Read it first.
